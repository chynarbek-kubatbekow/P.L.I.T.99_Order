# Проверка безопасности проекта

Проверка выполнена 28 октября 2026 года на локальной копии проекта. Проверялись код,
настройки Django, шаблоны, файлы загрузок, административный вход и HTTP-ответы.
Тесты атак используют отдельные базы с искусственными данными и слушают только
`127.0.0.1`. Это не аудит работающего production-сервера и не гарантия отсутствия
всех возможных уязвимостей.

## Исправления

| Область | Исправление |
| --- | --- |
| Утечка через ошибки | `DEBUG=False` по умолчанию; production отказывается запускаться с `DEBUG=True`. Страницы 400/403/404/500 не выводят настройки, пути и traceback. |
| Новости и XSS | HTML проходит allowlist-очистку `nh3` при сохранении и при выводе старых записей. Сохраняются абзацы, списки, заголовки, таблицы и безопасные ссылки. Скрипты, обработчики событий, опасные схемы URL и произвольные стили удаляются. Отключение autoescape убрано. |
| CSS и видео | Градиенты ограничены фиксированным синтаксисом. Видеоссылки принимаются только с точных HTTPS-хостов YouTube/Vimeo и преобразуются в embed-адреса. Старые значения дополнительно фильтруются при выводе; iframe получает sandbox. Сервер не скачивает эти URL. |
| Файлы | Проверяются содержимое JPEG/PNG/WebP, размер до 10 МиБ и до 20 млн пикселей. Файл декодируется и перекодируется, EXIF удаляется. Ошибка обработки отклоняет загрузку вместо сохранения исходного файла. Имена случайные. |
| Выдача media | Разрешены только проверяемые изображения. HTML/SVG, скрытые файлы, поддельные изображения, выход через `..`, обратные слеши и разрешённые за пределы корня ссылки не выдаются. Загружаемые файлы считаются публичными изображениями, не хранилищем конфиденциальных документов. |
| Права и CSRF | Сохранены серверные права Django admin и CSRF. Публичные обработчики принимают только GET/HEAD; параметрами запроса нельзя опубликовать новость. Черновики недоступны через публичные представления. |
| Административный вход | Общий для всех процессов счётчик в БД: до 20 POST-попыток с IP и до 10 на имя учётной записи за пятиминутное окно. Считаются также успешные попытки. Условный SQL UPDATE атомарен. При отказе БД вход закрывается с 503, превышение даёт 429 и Retry-After. Значения IP/имени хранятся как HMAC. |
| Пароли и сессии | Пароли, задаваемые через штатные формы и bootstrap-команду, проходят проверку с минимумом 12 символов. Сессии HttpOnly/SameSite=Lax, срок 8 часов, production-cookie только Secure. Существующие пароли автоматически не меняются. |
| Прокси и Host | Убрано безусловное доверие forwarded-заголовкам. Host проверяется для всех маршрутов, `ALLOWED_HOSTS=*` запрещён. Waitress по умолчанию слушает loopback. |
| Заголовки | CSP запрещает inline-скрипты, плагины и встраивание сайта в чужие фреймы; добавлены nosniff, Permissions-Policy и referrer policy. Аналитика перенесена из inline в локальный JS. Inline-стили оставлены для совместимости с текущей вёрсткой. |
| БД | ORM-запросы параметризованы; произвольного SQL из HTTP нет. SQLite PRAGMA использует allowlist. Для PostgreSQL заданы connection/statement/lock timeout; production требует SSL verify-full и отклоняет понижение через URL. SQLite/data-dir запрещено размещать внутри публичных static, SQLite также запрещена внутри media. |
| Конфигурация | Production требует постоянный сильный SECRET_KEY и HTTPS. Локальный ключ сохраняется вне Git. Сбой доступа к production data-dir не создаёт незаметно другую базу. Runtime, тестовые БД и окружения исключены из Git. |
| Зависимости и запуск | Все 12 runtime-пакетов закреплены точными версиями. Установка из wheel без исходных install scripts. Скрипты запуска проверяют ошибки команд, ограничивают размеры HTTP-запросов, заголовков, соединений и время канала. |

## Воспроизводимые проверки

Используйте отдельное виртуальное окружение Python 3.11+:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --only-binary=:all: -r requirements.txt
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test --noinput
python -m unittest scripts.test_deployment -v
python scripts/security_smoke.py
```

Если production-переменные уже заданы в терминале, для этих локальных тестов
установите `APP_ENV=local` и `SECURE_SSL_REDIRECT=False` только в тестовом процессе.
Не переключайте окружение запущенного публичного сервиса.

Проверка известных уязвимостей зависимостей в отдельном окружении инструментов:

```powershell
python -m pip install --only-binary=:all: pip-audit==2.10.0
python -m pip_audit -r requirements.txt --no-deps --disable-pip
```

После анализа документации: **86 тестов, 85 прошли, 1 пропущен**; **36 HTTP-проверок прошли**;
**12 runtime-пакетов, известных уязвимостей pip-audit не обнаружил**.
Первоначальные 43 теста и HTTP-проверки выполнены на Python 3.11 и в проектном
окружении `.venv` с Python 3.14.4. Расширенный набор из 86 тестов проверен на
Python 3.14.4; предыдущий этап — в [ACCESS_RECHECK.md](ACCESS_RECHECK.md), новый
разбор источников, находки и точный охват — в [SECURITY_RESEARCH.md](SECURITY_RESEARCH.md).
В `.venv` установлены закреплённые зависимости;
на существующей локальной SQLite применена `0003` после резервного копирования.
Целостность копии проверена, количество новостей и записей галереи сохранилось.
Восстановление этой копии в отдельную рабочую инсталляцию не выполнялось.
Пропущено создание реального symlink: Windows требует дополнительных прав или
Developer Mode. Проверки обычного traversal проходят. Параллельные попытки входа
проверены на SQLite; отдельная проверка конкуренции на PostgreSQL не выполнена.

`check --deploy` с production-конфигурацией не имеет ошибок, но сообщает два
предупреждения: HSTS для всех поддоменов и HSTS preload намеренно выключены.
Включать их можно после проверки HTTPS всех затронутых поддоменов. Production
`collectstatic` проверяется отдельно. Визуальная проверка браузером не завершена:
в среде отсутствуют подключённый браузер и рабочий native pipe Computer Use.

Перед публикацией повторно прошли 86 Django-тестов (один пропуск symlink),
36 HTTP-проверок и 7 отдельных тестов развёртывания. Последние проверяют PowerShell
и Bash в изолированной папке: production по умолчанию, выбор Python, отдельную роль
миграций, запуск без DDL и остановку при ошибках. Дополнительно копия только файлов
будущего коммита, без `.env` и локальных данных, прошла production check, миграции,
collectstatic и 12 проверок HTTPS-ответов/hashed static через Django test client.
Это проверка подготовки релиза на Windows с временной SQLite, не физического сервера.

Из индекса Git удалены ранее отслеживаемые тестовые SQLite и media; локальные файлы
сохранены. В тестовой SQLite не обнаружены пользователи, сессии или записи admin log.
Удаление из индекса не удаляет старый файл из истории Git; история не переписывалась.
Проверка шаблонов секретов в текущих файлах будущего коммита совпадений не дала;
она не заменяет полный аудит всей истории и не доказывает отсутствие любых секретов.

## Обновление существующей установки

Пошаговый редеплой, остановка службы, backup и откат описаны в
[REDEPLOY.md](REDEPLOY.md). Скрипты сборки и запуска теперь по умолчанию используют
production. `PYTHON_EXECUTABLE` задаёт Python службы независимо от системного PATH;
`build` применяет миграции, `start` только проверяет `migrate --check`.

1. Сделайте согласованную резервную копию БД и `APP_DATA_DIR/media`; проверьте
   восстановление на отдельной базе. Не публикуйте резервные копии в web-root.
2. Установите закреплённые зависимости в окружение сервиса.
3. Примените `python manage.py migrate --noinput`. Миграция `0003` добавляет только
   таблицу лимитов входа; существующие новости и пользователи не переписываются.
4. Выполните `python manage.py collectstatic --noinput`, проверьте настройки и
   перезапустите процесс сайта. Уже работающий старый процесс сам не обновится.
5. Проверяйте `/ddd//`, главную, новость, загрузку изображения и штатный вход.

В production задайте `APP_ENV=production`, `DEBUG=False`, сильный постоянный
`SECRET_KEY`, точные `ALLOWED_HOSTS` и `CSRF_TRUSTED_ORIGINS` с HTTPS. Возьмите
параметры из `.env.example`; секреты храните в защищённом env/менеджере секретов.
`manage.py` не загружает `.env` автоматически: её читают `manage.ps1`, `start.ps1`/`build.ps1`
и соответствующие shell-скрипты. Для ручных команд используйте `manage.ps1` либо
задайте те же переменные в окружении процесса. Shell-скрипты исполняют `.env` через `source`: этот файл
должен принадлежать доверенному оператору и быть недоступным для записи веб-процессу.

За IIS с HTTPS задайте `WAITRESS_TRUSTED_PROXY=127.0.0.1`, если IIS находится на
той же машине. IIS обязан удалять клиентские `X-Forwarded-For` и
`X-Forwarded-Proto` и устанавливать собственные. Waitress доверяет только указанному
адресу и передаёт Django проверенную схему и IP. Не используйте `*`, не открывайте
порт Waitress наружу. `TRUST_PROXY_HEADERS` обычно оставляйте False: схема уже
передаётся Waitress через WSGI. При другом сервере этот флаг допустим только за
прокси, который гарантированно перезаписывает заголовки.

Скрипты старта не создают superuser автоматически. Для первоначального создания
используйте явную команду `createsuperuser` или `create_admin_if_missing`.
Старые пароли проверьте и смените самостоятельно, если они слабые. Удалите
`DJANGO_SUPERUSER_PASSWORD` из постоянного окружения после первоначального создания
пользователя. Раздавайте сотрудникам минимальные model permissions; superuser —
только оператору. Для дополнительной защиты админки ограничьте её доступ через
VPN/IP и MFA на доверенном входном прокси. Встроенная MFA в этой версии не добавлена.

Ежедневно запускайте `python manage.py clear_login_throttles` и
`python manage.py clearsessions` из окружения сервиса. Лимит по аккаунту затрудняет
распределённый перебор, но позволяет временно исчерпать окно чужого аккаунта;
для публичной админки дополнительно нужен rate limit на прокси. Фиксированные окна
также допускают краткий всплеск на их границе.

## Что необходимо проверить на настоящем сервере

- TLS/сертификат и перенаправление HTTP→HTTPS, работа CSP с реальными интеграциями.
- PostgreSQL доступен только приложению/оператору. Runtime-роль не superuser, без
  CREATEDB/CREATEROLE/BYPASSRLS; для миграций — отдельная роль с DDL. Минимальные
  GRANT на нужные таблицы/sequence, закрытый firewall, SCRAM, защищённые backup.
  Для удалённой БД используйте `sslmode=verify-full` и доверенный CA; не понижайте
  SSL в URL. Проверьте действующие роли, pg_hba.conf и восстановление backup.
- Системный пользователь приложения не администратор ОС, исходники и `.env`
  доступны ему только на чтение; запись — только в data/temp. На Windows режимы
  `0600/0700` не заменяют настройку NTFS ACL. IIS не должен раздавать каталог проекта.
- Proxy rate limit и ограничения ресурсов против DoS, обновления ОС/Python,
  мониторинг 403/429/5xx без записи паролей/cookie. Высоконагрузочный DoS не тестировался.
- Реальные роли сотрудников, MFA/VPN, журнал изменений Django admin. Сервер может
  проверить полномочия автора, но не истинность фактов в новости: для этого нужны
  редакционная проверка и процесс публикации. Украденный аккаунт с правом публикации
  всё ещё может публиковать ложный текст.

DevTools показывает всё, что браузер получил: публичные URL, HTML, CSS и JS нельзя
скрыть от посетителя. Изменение DOM на своём компьютере не меняет серверную БД.
Защита состоит в серверных правах, CSRF и проверке данных, а не в запрете F12.
