# Повторная проверка доступа к БД и бэкенду

Этот отчёт описывает этап с 55 тестами. Последующий анализ источников и результаты
расширенного набора находятся в [SECURITY_RESEARCH.md](SECURITY_RESEARCH.md).

Дата: 28 октября 2026 года. Область: эта локальная копия проекта, работающий
HTTP-сервис на `127.0.0.1:8000`, локальные слушающие порты и доступные конфигурации.

**Результат:** в выполненных проверках получить несанкционированный доступ к данным
или административным операциям не удалось. Это не доказательство невозможности
взлома и не проверка доступности сервера из Интернета.

## Приложение

- Сейчас используется SQLite, а не установленный на компьютере PostgreSQL.
  Ручной запуск и `.env` указывают на одну базу. Миграции применены, таблица лимитов
  входа существует. Содержимое новостей и пользователей не менялось при проверке.
- Файл БД находится вне каталогов static/media. На работающем HTTP-сервисе
  запросы БД, `.env`, runtime-путей и traversal вернули 404 без SQLite-содержимого
  или отладочной информации. Административные GET-запросы без сессии дали 302 на вход.
- Подмена cookie, роли в теле запроса/заголовках и сессии без корректного
  authentication hash не предоставила доступ. Неактивный superuser не допускается.
  Staff с правом просмотра не может редактировать/удалять новости и читать пользователей.
- SQL-инъекции в имени/пароле не авторизовали пользователя; подмена параметров
  публичных страниц не изменила записи. Недоступны предполагаемые API, debug,
  dump/backup и служебные маршруты. Django admin не отдаёт ответы в публичный кэш.
- Публичные исходные ресурсы не содержат проверенных SECRET_KEY или сохранённого
  bootstrap-пароля; файлы БД, SQL, `.env` и backup среди static не обнаружены.
  Это адресная проверка известных секретов, не универсальный поиск всех секретов.
- Для `.env`, каталога данных, SQLite и backup не обнаружены ACE с доступом для
  Everyone, Authenticated Users, Builtin Users или Anonymous. Это не полный аудит
  NTFS, групп и локальных администраторов ОС.

Добавлены 12 отрицательных проверок в `core/test_access_control.py`. Полный набор:
**55 тестов, 54 прошли, 1 пропущен** (symlink требует прав Windows).
Новый тестовый набор выполняет записи только в одноразовую тестовую БД. На реальном
HTTP-сервисе использованы только GET; рабочий пароль администратора не подбирался.

## Найденный риск запуска и исправление

В защищённом `.env` сохранились параметры bootstrap-администратора. Такой учётной
записи в текущей базе нет; раньше `start.ps1`/`start.sh` могли создать дополнительный
superuser при следующем старте. Автоматический вызов удалён. Первичное создание
теперь выполняется только явной командой оператора. Существующие учётные записи
и пароли не менялись. Сохранённый bootstrap-пароль рекомендуется убрать из `.env`,
если он больше не нужен; его значение нигде не записывалось в отчёт.

## PostgreSQL и сеть

- Сервис PostgreSQL слушает порт **5432 на всех IPv4/IPv6-интерфейсах**. Веб-сервер
  на порту **8000 слушает только loopback**.
- В доступном `pg_hba.conf` обнаружены только local/loopback-правила с
  `scram-sha-256`; правил `trust` и правил для удалённых клиентов нет. В проверенных
  основном/auto-конфигах не обнаружены include или переопределение `hba_file`;
  в командной строке службы также не найдено перенаправление config/hba.
- По IPv4 и IPv6 отправлен только стартовый протокольный пакет для стандартной
  роли `postgres`: сервер запросил SASL/SCRAM. Пароль и SQL-запросы не отправлялись.
  Обход аутентификации при этих локальных попытках не обнаружен.
- Профили Windows Firewall включены. В ActiveStore не обнаружены явные разрешающие
  правила для порта 5432 или программы postgres. Общие правила, маршрутизатор,
  групповые политики и реальная доступность с другой машины полностью не проверены.

Слушающий порт сам по себе не означает доступ без пароля: доступ также определяют
правила аутентификации и сеть. См. [PostgreSQL: подключения](https://www.postgresql.org/docs/current/runtime-config-connection.html)
и [pg_hba.conf](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html).
Если удалённые подключения не нужны, стоит ограничить PostgreSQL до localhost.
Настройки системного PostgreSQL и firewall не изменялись: этот проект использует
SQLite, а системная служба может обслуживать другие приложения.

## Что результат не покрывает

Не проверены доступность из Интернета, размещённый на другом сервере экземпляр,
перехваченные действующие сессии, компрометация ОС/учётной записи владельца,
неизвестные уязвимости и фактическая стойкость существующего пароля администратора.
Установленная MFA отсутствует. Если сайт размещается публично, отдельно проверьте
HTTPS, входной прокси, доступ к админке и внешние сетевые правила по `SECURITY.md`.
