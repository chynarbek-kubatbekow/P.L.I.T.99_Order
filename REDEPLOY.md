# Обновление физического сервера из GitHub

Репозиторий содержит код, миграции, зависимости и скрипты запуска. GitHub не
переносит `.env`, рабочую БД, загруженные фотографии, TLS-сертификаты и настройки
IIS/службы. Они сохраняются на сервере отдельно. Первичная установка Windows —
в [WINDOWS_DEPLOY.md](WINDOWS_DEPLOY.md); результаты аудита — в [SECURITY.md](SECURITY.md).

Для текущего Linux + nginx используйте раздел «Повторный деплой Linux» ниже.
Локальные `run-local.ps1` / `run-local.sh` в запуске серверной службы не участвуют.

## Перед первым запуском

- Настройте `.env` по `.env.example`: `APP_ENV=production`, `DEBUG=False`, постоянный
  случайный `SECRET_KEY` длиной от 50 символов, точные домены и HTTPS origins.
- Укажите абсолютные `APP_DATA_DIR` вне каталога кода и `PYTHON_EXECUTABLE`, например
  `C:/plit99/venv/Scripts/python.exe`. Существующие данные нужно перенести отдельно,
  сохранив структуру `media/`; смена пути не копирует файлы автоматически.
- PostgreSQL: отдельная runtime-роль без DDL, SCRAM, TLS `verify-full` с доверенным
  CA и соответствующим именем сервера. Порт БД доступен только необходимым узлам.
  Роль владельца схемы используется оператором при сборке; её URL передаётся как
  `MIGRATION_DATABASE_URL` только в окружение процесса сборки, вне service `.env`.
- IIS завершает TLS и проксирует на `127.0.0.1:8000`. Внешние forwarded-заголовки
  заменяются доверенными, исходный публичный Host сохраняется. Доверяйте только
  точному адресу прокси. Внешний доступ к Waitress и каталогу проекта запрещён.
- Служба работает под отдельной учётной записью с минимальными NTFS-правами.
  Админка дополнительно ограничивается VPN/IP на прокси, MFA — на шлюзе доступа.
  Эти настройки не устанавливаются одним `git pull`.

## Повторный деплой Windows

1. Проверьте `git status --short` на сервере и сохраните локальные изменения.
   Зафиксируйте текущий commit: `git rev-parse HEAD`. Не заменяйте серверный `.env`
   примером из репозитория и не запускайте `seed_data` на рабочей БД.
2. Остановите службу и другие процессы записи. Сделайте согласованную резервную
   копию БД, `APP_DATA_DIR/media`, `.env` и конфигурации IIS/службы вне webroot.
   Для PostgreSQL используйте `pg_dump -Fc` с защищённой передачей пароля, для
   SQLite — backup API SQLite или копию после остановки всех писателей. До
   обновления убедитесь, что копия восстанавливается в отдельное окружение.
3. Обновите код без автоматического merge. Пример предполагает службу `plit99`
   и каталог `C:\plit99\app`; при других именах замените их заранее:

   ```powershell
   C:\nssm\nssm.exe stop plit99
   Set-Location C:\plit99\app
   git pull --ff-only
   if ($LASTEXITCODE -ne 0) { throw "Git update failed." }
   # PostgreSQL: оператор заранее передаёт MIGRATION_DATABASE_URL через
   # защищённое окружение этого процесса, не через командную строку или Git.
   .\build.ps1
   if (-not $?) { throw "Build failed; service must remain stopped." }
   Remove-Item Env:MIGRATION_DATABASE_URL -ErrorAction SilentlyContinue
   C:\nssm\nssm.exe start plit99
   ```

   При ошибке не переходите к следующему шагу. `build.ps1` применяет миграции;
   `start.ps1` только проверяет их наличие и запускает Waitress выбранным Python.
   Для первого администратора используйте `.\manage.ps1 createsuperuser`.

4. Через публичный HTTPS-домен проверьте главную, новости, фотографии, CSS/JS,
   вход/выход администратора и сохранение новости. Запрос неизвестного пути должен
   давать обычную 404 без списка маршрутов; `.env`, `.git/config`, SQLite и
   резервные копии не должны скачиваться. Проверьте запрет записи без CSRF и
   авторизации, отсутствие циклического HTTPS-редиректа и сохранность данных.
5. Проверьте автозапуск после перезагрузки, журналы без секретов и планировщик
   `.\manage.ps1 clearsessions` / `.\manage.ps1 clear_login_throttles`.

Для Linux предусмотрены `build.sh` / `start.sh` с теми же этапами и
`PYTHON_EXECUTABLE`; конфигурация systemd, reverse proxy, TLS и прав ОС выполняется
отдельно. Инструкции NSSM/IIS относятся к Windows.

## Повторный деплой Linux + nginx

Порядок существующего деплоя сохраняется: stop → проверенный backup →
`git pull --ff-only` → `bash build.sh` → прежняя служба с `bash start.sh`.
Имя systemd-службы, путь приложения и настройки nginx должны оставаться
фактическими серверными, а не копироваться из примеров Windows.

1. Зафиксируйте текущий commit, состояние Git и конфигурацию службы. Остановите
   писателей и создайте восстанавливаемую копию БД/media. Ключ шифрования отзывов
   сохраните отдельно от БД. Не удаляйте `.env` и не переносите на Linux локальные
   Windows-пути, тестового администратора или файл с его паролем.
2. Сохраните прежние `DATABASE_URL`, `APP_DATA_DIR`, `SECRET_KEY` и ключ отзывов.
   Смена пути не переносит данные. Переход SQLite→PostgreSQL — отдельная процедура,
   не автоматический шаг этого обновления. `seed_data` на рабочей БД не запускайте.
3. Обновите код и выполните `bash build.sh` в прежнем защищённом окружении.
   Build устанавливает закреплённые зависимости, выполняет check/collectstatic и
   миграции. `0004` добавляет отзывы/видео, `0005` обновляет metadata поля видео.
   При раздельных DB-ролях DDL выполняет `MIGRATION_DATABASE_URL` только в процессе
   сборки; runtime-служба не получает owner-пароль.
4. Если отзывы ещё не были настроены, задайте приватный
   `FEEDBACK_ENCRYPTION_KEY_FILE` или `FEEDBACK_ENCRYPTION_KEYS`. Для нового
   файла можно вызвать `create_feedback_key` в том же production-окружении
   через выбранный Python. Если отзывы уже есть, используйте существующий ключ,
   не создавайте замену. Ключ должен читаться учётной записью службы и не
   находиться в static/media. Не выводите ключ в команды, Git или логи.
5. Служба по-прежнему запускает `start.sh`, а не `run-local.sh`. Production требует
   HTTPS и Secure-cookies. При nginx на той же машине upstream остаётся
   `127.0.0.1:8000`; `WAITRESS_TRUSTED_PROXY=127.0.0.1`. Nginx заменяет входящие
   X-Forwarded-For/Proto, сохраняет Host и завершает TLS. Не открывайте Waitress
   и БД наружу. Если раньше конфигурация работала, не заменяйте её целиком.
6. Проверьте `nginx -t` перед reload при изменении nginx. Для загрузки видео
   до 100 МиБ нужны соответствующие лимиты proxy (до 112m на административную
   multipart-загрузку). Не раздавайте `/media/videos/` напрямую мимо Django:
   это обойдёт проверку черновиков. Не раздавайте каталог проекта как webroot.
7. После перезапуска откройте по HTTPS свежие страницы входа и контактов,
   проверьте вход, отправку отзыва, его чтение в admin, сохранение новости,
   фото/видео и закрытые приватные пути. На формах должен быть единственный
   эффективный `Referrer-Policy: same-origin`. Если nginx добавляет собственный
   `no-referrer`, исправьте именно это правило: оно ломает нативные POST-формы.
   Чужой Origin и `Origin: null` должны по-прежнему получать 403.

Локальные и серверные команды используют общий код и миграции, но разные
HTTP/TLS-настройки. Локальный профиль меняет окружение только дочернего процесса;
production `.env` и существующая БД автоматически не переписываются.

## Откат

Сначала остановите службу. Верните предыдущий проверенный commit без удаления
серверных данных, установите его зависимости и пересоберите его статику. Это
достаточно только при совместимой схеме БД. Если схема несовместима, восстановите
согласованные БД и media из проверенной копии; учитывайте потерю записей после
момента backup. Не выполняйте обратные миграции вслепую. После восстановления
повторите проверки HTTPS, админки и данных.

## Локальная проверка подготовки релиза

```powershell
.\.venv\Scripts\python.exe manage.py test --noinput
.\.venv\Scripts\python.exe -m unittest scripts.test_deployment -v
.\.venv\Scripts\python.exe scripts/security_smoke.py
```

Тесты скриптов используют временную папку и подменные команды без установки
пакетов и без рабочей БД. Они проверяют PowerShell и Bash, production по умолчанию,
выбор Python, разделение роли миграций и службы, ограничения HTTP и остановку при
ошибках. Они не подтверждают настройки вашего физического сервера.
